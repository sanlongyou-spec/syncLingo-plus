## 三、排查得到的关键结论（重要，避免日后走弯路）

### 1. 06-19 的崩溃不是内存 OOM，而是 CPU
- 多轮监控显示：后端内存峰值 < 2.3G、系统可用始终 > 1.8G、无 swap、容器 `OOMKilled=false`、`Restarts=0`。
- 真正瓶颈是 **CPU**：连接**集中涌入瞬间**（开会时几十人同时点开分享链接）CPU 冲到 ~300–400%（4 核打满）→ 卡死 → 客户端重连风暴 → 雪崩。
- 「3g 堆」是误判：命令行 `-e` 实际生效一直是 2g。
- 隐形放大源：分享页每 3 秒拉「不断增大的历史 JSON」，听众越多、会议越长越费带宽/内存/CPU。

### 2. 单机合成压测测不准
- 外部单 IP 猛连 → 被 nginx/边缘**限流**；服务器本机压 → 压测进程与后端**抢 CPU**；会话不出声 → 音频连接掉。
- 要真测高并发需多 IP / 真人，或边缘放开限流。

### 3. Bot 通知失效的根因（今天）= 与代码无关
- 现象：通知报 `no conversationUpdate arrived within 8 s`，连「之前无感自动收到」的老用户也收不到。
- 机制：Bot 把每个用户的「投递地址」(ConversationReference) **只存内存**（`ConversationReferenceCache` 用 `IMemoryCache`，7 天过期）。地址在用户「首次被通知」时由 Teams 的 conversationUpdate 自动捕获并缓存，全程用户无感。
- 真因：**Bot 重启清空了内存缓存**；对**已安装**的老用户，Teams 不会因重启再发 conversationUpdate，`GET /chat` 触发后也常需数十秒（>8s）才回投 → 超时失败。
- 已验证**不是接收端点问题**：nginx `location = /api/messages → 127.0.0.1:3978` 正常，裸 curl 经 nginx 打 `/api/messages` 返回 401（Bot 在响应）。安装与 `GET /chat` 触发均成功（日志可见），唯独 conversationUpdate 不在 8s 内回投，且全程无 `Stored personal ConversationReference`。
- 回退到 8s 仍失败 → 确认非今日代码引入。
- **建议的正确修复方向（日后做）**：
  1. **持久化** ConversationReference（存盘+启动加载），重启不丢——根治「重启后老用户收不到」；
  2. 适当**加长等待**（如 45s；install/poll 为并行执行，不随人数线性累加）以提高自动重建成功率；
  3. 注意：已丢失的历史地址需每人被成功投递/捕获一次才会重新入库（之后持久化保持）。

### 4. 「点链接看到旧版、复制到浏览器正常」= 前端缓存，非版本并存
- 前端为 Vite SPA：`index.html`（入口）+ 带哈希名的 JS（如 `index-XXXX.js`，实际程序）。
- 一天内多次部署，JS 文件名变了多次；浏览器/Teams 内置浏览器把**旧 JS 缓存**了。
- **点链接/旧标签** → 命中缓存的旧文件 → 看到「今天改过的旧版本」；
  **复制到新标签** → 重新取最新文件 → 正常（当前版本）。
- 用户侧应急：`Ctrl+Shift+R` 强刷或无痕窗口。
- **根治（建议做一次）**：nginx 对 `index.html` 加 `Cache-Control: no-cache`
  （带哈希名的 JS/CSS 可长期缓存，改名即自动失效），从此部署后不再看到旧缓存。
